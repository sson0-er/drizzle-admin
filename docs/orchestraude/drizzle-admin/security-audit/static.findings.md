## medium

- [auth.findings] Session cookie is not bound to the admin instance; a shared secret lets a session from one admin log in to another
  - location: src/auth/session.ts:76
  - detail: readSession accepts any da_session value whose HMAC verifies under config.secret. The signed payload is only {u, csrf, iat}, and hono's makeSignature signs the value alone (not the cookie name, path or instance). So when a host runs two createAdmin instances with the same secret (a single ADMIN_SECRET env var reused for two instances, e.g. basePath /staff with a verifyCredentials over staff accounts and /ops with one over superusers), a session issued by one instance is a valid login on the other. Attack: a low-privileged user logs in at /staff, copies the da_session value from their own browser devtools and sets it with Path=/ops (or sends it with curl). Then GET /ops/ returns 200 as that user, and with the default permissions (all true) they get full CRUD on the /ops models. Reproduced at HEAD with two in-process instances sharing a secret: the POST /staff/login/ cookie gives 200 on GET /ops/ with no redirect to login. The README says nothing about using a separate secret per instance. The same lack of domain separation also means da_flash and da_session values are interchangeable at the signature level. Today only their JSON shapes keep them apart (array vs object), which holds now but breaks if either payload changes. Fix: derive per-purpose keys, e.g. HMAC(secret, `da_session\0${prefix}`) and HMAC(secret, `da_flash\0${prefix}`), and use those as the signing secrets. Or add the prefix (an instance tag) to the session payload and reject a mismatch in parseSession. Document in the README that each admin instance needs its own secret, distinct from any secret the host uses elsewhere.
  - evidence: (none)
- [authz.findings] Rows of a model whose view is denied can be read through the delete, bulk-action and change-POST pages
  - location: src/routes/actions.ts:66-71, src/routes/actions.ts:100-104, src/routes/form.ts:245-278, src/routes/delete.ts:25-45
  - detail: view gates only the list, the dashboard entry and the change GET. The other handlers check only their write permission and still render stored row data. Permissions default to allowed when unset (README: 'An unset entry allows the operation'). So a realistic config such as `permissions: { view: (u) => u.role === 'admin' }` hides the model from the dashboard and the list but leaves delete, change and add open to every logged-in user. Attack, verified with a probe against the fixture DB (authors registered with view:false, toString showing name and email, readonlyFields ['email']): a logged-in non-admin (1) takes any _csrf token from the dashboard, then (2) POSTs /admin/authors/ with action=delete_selected&_selected=1&_selected=2&...&_selected=N and no _confirm. The response is a 200 confirmation page listing pk and toString for every existing id ('alice <alice@example.com>', 'bob <bob@example.com>', ...). Sweeping ids enumerates the whole table, and nothing is deleted without _confirm=1. The same works with a custom action that has confirm:true when change is allowed. (3) POST /admin/authors/2/change/ with name= (invalid) returns 400 with the title 'change: bob <bob@example.com>', and displayRow renders the stored values of the read-only fields ('bob@example.com' is in the HTML). (4) GET /admin/authors/3/delete/ returns 200 with the object label. A valid save also flashes the label. With the default change/delete the same user can also modify and delete the rows they cannot view. The read path contradicts README 'Permissions' ('view: dashboard entry, list page and the change page'): step 3 renders the change page without view. It also contradicts the CLAUDE.md rule 'Values the user may not see are not rendered'. Fix (needs a decision record): either (a) make unset add/change/delete inherit the resolved view value, so restricting view alone fails closed, or (b) also require view before any page renders rows: the delete_selected and custom-action confirmation pages, the change POST (or at least its 400 re-render and success flash) and the delete GET. Django gates the changelist (where actions run) on view-or-change. Then add permission-matrix tests for a user who has delete/change but not view.
  - evidence: (none)

## low

- [auth.findings] External-mode login redirect forwards a protocol-relative next (//evil.com/) to the host's loginUrl when basePath is "/"
  - location: src/routes/middleware.ts:80
  - detail: authGuard builds target from the raw request pathname. With basePath "/" (prefix ""), a request for http://admin.example.com//evil.com/ reaches the guard, and in external mode it answers 302 to `${loginUrl}?next=%2F%2Fevil.com%2F` (reproduced at HEAD). The library's own login runs next through safeNext, but in external mode the host's login page receives the value. A host that checks next with the common startsWith("/") test then redirects to //evil.com/ after login. That is an open redirect that starts from a link on the admin's own domain. It needs a weak check in the host, so this is hardening. Fix: in external mode, pass the target through the same normalization as safeNext (or fall back to `${prefix}/` when the pathname starts with "//"), and say in the README that the host must validate next.
  - evidence: (none)
- [auth.findings] sessionMaxAgeSec above 400 days is accepted but makes every session write throw (all pages 500)
  - location: src/admin.ts:73
  - detail: resolveConfig only requires a positive integer. hono's cookie serializer throws when Max-Age > 34560000. So with, for example, sessionMaxAgeSec: 40000000, every request that writes a session (each anonymous GET, and every login) ends in onError with 500. Reproduced at HEAD: GET /admin/login/ returns 500 and logs "Cookies Max-Age SHOULD NOT be greater than 400 days". It fails closed, so this is not exploitable, but it is a config-validation gap in the cookie path. Fix: reject sessionMaxAgeSec > 34560000 in resolveConfig with a drizzle-admin: message.
  - evidence: (none)
- [authz.findings] Unknown model slug returns 404 but a registered model without view returns 403
  - location: src/routes/context.ts:106-108, src/routes/list.ts:116-121
  - detail: Every model handler runs modelOr404 before the permission check. A logged-in user can therefore probe GET /admin/<slug>/ and tell registered-but-forbidden models (403) from unregistered ones (404), which reveals the names of hidden models (usually table names). Impact is small because the probe needs a login and slugs are rarely secret. Hardening: answer 404 when the user lacks view on a registered model, or accept and record it. The change and delete routes already check permission before the row lookup, so there is no row-existence oracle.
  - evidence: (none)
- [data.findings] Input the DB rejects on GET/list paths returns 500 instead of 404 or an ignored value
  - location: src/data/query.ts:96
  - detail: parseFieldValue/parsePk accept any safe integer and any string, but the DB rejects some of them, and the error escapes to onError as a 500. Verified with tsx against the test fixtures: on PostgreSQL, GET /admin/authors/3000000000/change/ (serial int4 PK) -> 500 (22003); GET /admin/articles/?f_authorId=3000000000 -> 500 (22003); GET /admin/articles/?q=%00 -> 500 (22021, NUL byte in a text parameter). A uuid PK or FK filter with a non-uuid string fails the same way (22P02). On SQLite, POST /admin/articles/ with action=delete_selected and 40000 _selected values -> 500 (SQLITE_ERROR, more than 32766 bound variables in getMany). Attack scenario: any logged-in user with view sends these URLs repeatedly. They get 500 pages and a server-log line per request; no data leaks, because the log line is only '<kind> <name> <code>'. Fix: range-check integer PK/FK values by column type (int2/int4) in parseFieldValue so they return null (-> 404 or filter ignored); strip or reject NUL in q before buildSearch; cap the number of _selected ids (for example at a few thousand) before getMany/delete. Also consider treating a pg 22P02/22003 from get() as not found.
  - evidence: (none)
- [data.findings] Search term has no length cap; every search is an unindexable scan plus count(*)
  - location: src/data/query.ts:27
  - detail: buildSearch uses the whole trimmed q with no length limit, and list() runs count(*) plus the page query with '%term%' LIKE/ILIKE OR-ed across all searchFields. On PG every column is cast with ::text, so no index can be used. Attack scenario: a logged-in user with view on a large table scripts GET /admin/<model>/?q=<several KB of text>&p=<n> in a loop. Each request forces two full scans per searchField, which costs DB CPU out of proportion to the request. Only the HTTP server's URL limit bounds it. Fix: truncate or reject q above a fixed length (for example 200 characters) in listHandler before calling repo.list. This is hardening only; it needs an authenticated user.
  - evidence: (none)
- [data.findings] Integer coercion silently rounds unsafe integers and accepts hex/exponent notation
  - location: src/forms/coerce.ts:34
  - detail: For kind number with isInteger, parseByKind uses Number(trimmed) plus Number.isInteger. Input such as '9007199254740993' becomes 9007199254740992 and is stored without an error. On SQLite integer and PG bigint mode 'number' columns, that is a different value from the one the user typed. '0x1F', '0b11' and '1e3' are also accepted as 31, 3 and 1000. This disagrees with parseFieldValue in src/data/query.ts, which requires /^-?\d+$/ and Number.isSafeInteger. Impact is data integrity rather than a privilege gain: a user with add/change permission submits a large ID-like value (for example an external account number), and a different value is persisted without any warning. Fix: for isInteger require /^-?\d+$/ and Number.isSafeInteger, and reject anything else with invalidInteger; for non-integer numbers require a plain decimal pattern.
  - evidence: (none)
- [data.findings] Non-PK identity columns are introspected as editable
  - location: src/introspect/index.ts:130
  - detail: isGenerated checks only column.generated. isAutoIncrement checks generatedIdentity only for primary keys. A non-PK integer().generatedAlwaysAsIdentity() column therefore comes out as kind number, hasDefault true, isGenerated false (verified with introspectTable), so the add and change forms render it as an editable input. On PG a GENERATED ALWAYS identity rejects explicit values. Every change-form save then sends the prefilled value and fails with a generic dbOther error. For GENERATED BY DEFAULT identity columns, any editor can overwrite a DB-managed sequence value. Fix: set isGenerated (or an equivalent lock) when column.generatedIdentity !== undefined, so such columns are display-only like other generated columns. This is outside the strict security scope; I report it because it is a DB-managed field that the form exposes for writing.

- [views.findings] No Content-Security-Policy or X-Content-Type-Options header
  - location: src/routes/middleware.ts:22
  - detail: securityHeaders sets X-Frame-Options, Referrer-Policy and Cache-Control but no CSP and no `X-Content-Type-Options: nosniff`. Today every output is JSX-escaped, so there is no injection to contain. The gap is defence in depth only: if a later change or a host-supplied formatter path ever reached raw HTML, nothing would limit the script to the admin's own code. A strict CSP would be `default-src 'none'; style-src 'self'; script-src 'sha256-<hash of SELECT_ALL_SCRIPT>'; form-action 'self'; frame-ancestors 'none'; base-uri 'none'`. The script is a constant, so its hash can be computed once at module load. Also add `X-Content-Type-Options: nosniff`. Hosts can still add these headers themselves, so this is optional hardening (design routes.md step 1 does not list them; adding them needs a decision record).
  - evidence: (none)
- [views.findings] Default listDisplay ignores `exclude`, so excluded columns still show in the list
  - location: src/admin.ts:223
  - detail: When `listDisplay` is not set, the list shows the primary key plus the first four other columns, chosen without looking at `exclude`. Scenario: an operator registers `users` with `exclude: ["apiToken"]` (or a password-hash column without the password widget), believing the column is hidden. A user who only has `view` opens GET /admin/users/ and sees the token in plain text in a list cell. The README says `exclude` only affects the form, so this is documented behaviour, but it is a footgun of the same kind decision 037 Q7 rejected for password columns ("the default listDisplay can show the value without the operator choosing it"). - [views.findings] Example demo with its default password can be taken over by DNS rebinding
  - location: example/server.ts:6
  - detail: The demo binds to 127.0.0.1 (decision 038) but accepts any Host header, and its default password is the publicly known `admin`. Scenario: a developer runs `pnpm example` and visits an attacker page at attacker.example:3000, which rebinds to 127.0.0.1. Script on that page, now treated by the browser as same-origin with the demo, does GET /admin/login/ (reads the session cookie and _csrf token) and then POST /admin/login/ with admin/admin. The Origin check passes because Sec-Fetch-Site is same-origin and Origin matches the Host-derived request URL. The attacker can then read and modify all demo data. The impact is limited to the seeded in-memory demo, but developers often copy the example onto a real database. Fix: in example/server.ts, reject requests whose Host is not 127.0.0.1:<port>, localhost:<port> or [::1]:<port> (a small Hono middleware). Setting publicOrigin alone does not help, because Sec-Fetch-Site: same-origin still passes.
