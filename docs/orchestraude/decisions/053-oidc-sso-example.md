# 053: OIDC SSO example with @hono/oidc-auth and an https mock IdP

- Date: 2026-10-09
- Status: accepted
- Changed 2026-10-10: points 12-14 added (user answers to Q19-Q21); points 4 and 11 refer to them.
- Changed 2026-10-10 (design review, OIDC round): point 2 adds the behavioural negative control, more scanned names and files, and the one exempted refusal; points 3 and 6 rewritten; point 7 notes the CLAUDE.md scope; point 15 added (explicit library settings, real-mode scopes).

## Context
Scope change (01-requirements.md, 2026-10-09): an example of external auth mode (`auth.getUser` + `auth.loginUrl`, decisions 044 and 047) signing in through OpenID Connect, runnable offline, plus an automated test of the whole flow in CI. The user fixed the main choices (library, mock IdP, TLS handling, launcher, real-IdP mode, `next` validation, logout, README caveats, exact dev pins). This record fixes how the pieces fit and the choices left to the designer. Research: 02-research.md "OIDC example (2026-10-09)" and "Follow-up: option B".

## Decision
1. **Library and mock IdP (user decision).** The example uses `@hono/oidc-auth` 1.10.0 as the relying party and `oidc-provider` 9.12.2 as an in-process mock IdP with `devInteractions` (any user name, password ignored). New exact-pinned devDependencies: `@hono/oidc-auth` 1.10.0, `oidc-provider` 9.12.2, `@types/oidc-provider` 9.12.1, `selfsigned` 5.5.0. No runtime dependency of the package changes; `files` is unchanged, so none of this is published.
2. **TLS (user decision).** The mock IdP serves `https://localhost:<port>` (bound to `127.0.0.1`) with an EC P-256 / sha256 certificate (SAN `localhost`, `127.0.0.1`, `CA:FALSE`, 30 days) generated at run time by `selfsigned` into a fresh `mkdtemp` directory. Node trusts it only through `NODE_EXTRA_CA_CERTS`, set at process start: by the launcher for the example and by a vitest `globalSetup` for the tests. TLS verification is never disabled: the strings `NODE_TLS_REJECT_UNAUTHORIZED`, `rejectUnauthorized` and `allowInsecureRequests` must not appear in `src/`, `test/`, `example/`, `scripts/`, `.github/`, `package.json`, `vitest.config.ts`, `tsconfig*.json` or `mise.toml` (guard test, excluding the guard file itself), and the guard test also asserts that `NODE_TLS_REJECT_UNAUTHORIZED` is unset in the test workers. Changed 2026-10-10 (design review): the scan also covers `checkServerIdentity`, `strict-ssl`, `strictSsl` and `--insecure`, and `.npmrc` / `pnpm-workspace.yaml` when present. The behavioural proof is a negative control in the flow test's own worker: an https server with a second generated certificate, not in `NODE_EXTRA_CA_CERTS`, must be rejected by `fetch` (`DEPTH_ZERO_SELF_SIGNED_CERT`), which fails whatever mechanism disabled verification. The example itself refuses to start (launcher and server) when `NODE_TLS_REJECT_UNAUTHORIZED` is `"0"`; that check in `example/oidc/mode.ts` is the single exempted occurrence of the name, and the guard requires exactly one occurrence there.
3. **Launcher (user decision).** Changed 2026-10-10 (design review): the mode rule (`OIDC_ISSUER` non-empty → real, else mock) lives only in `example/oidc/mode.ts` and is used by the launcher and `config.ts`; running `server.ts` directly in mock mode, or with both `OIDC_ISSUER` and `OIDC_MOCK_CERT_DIR`, fails with a message naming `pnpm example:oidc`; every startup error has a fixed text (example-oidc.md). `pnpm example:oidc` runs `tsx example/oidc/launch.ts`. Without `OIDC_ISSUER` (mock mode) it writes the certificate, then spawns `process.execPath --import tsx example/oidc/server.ts` with `NODE_EXTRA_CA_CERTS=<dir>/cert.pem` and `OIDC_MOCK_CERT_DIR=<dir>`, forwards SIGINT/SIGTERM, removes the directory when the child exits and exits with the child's code. With `OIDC_ISSUER` set (real-IdP mode) it spawns the same child with the environment unchanged: no mock, no generated certificate, no extra CA. One child process hosts both the mock IdP and the app.
4. **getUser bridge.** A per-app `WeakMap<Request, AdminUser>` is filled by a middleware on `/admin/*` that calls `getAuth(c)`; `auth.getUser(req)` returns `map.get(req) ?? null`. The admin is mounted with `app.route("/admin", admin.app)` so the admin sees the same `Request` object (`c.req.raw`) as the outer middleware. A miss means "not signed in" (fail closed). Only allowlisted users are put into the map; others get a 403 there (point 12). One global `app.use("*", initOidcAuthMiddleware(config))` configures the library once per request.
5. **Login and return.** `loginUrl` is `/oidc/login`. `GET /oidc/login` runs `oidcAuthMiddleware()` (so the library's `continue` cookie always holds this login URL including `?next=`), and its handler redirects 302 to `safeReturnPath(next, "/admin")`, an example-local copy of the `safeNext` rules (same-origin path under `/admin/`, fallback `/admin/`), because `safeNext` is internal (user decision). The library's `continue` cookie and the redirect after the callback are not validated by the library; the example relies on the login route being the only place `oidcAuthMiddleware` runs and on `hostGuard` (decision 048) restricting `Host`, from which `continue` is built.
6. **Callback.** `GET /oidc/callback` calls `processOAuthCallback(c)` explicitly. Changed 2026-10-10 (design review): any error it throws is caught; the example deletes the four flow cookies (`Path=/oidc/callback`), logs only the error's name and answers a generic 400 "Sign-in failed" page, because the library's `HTTPException` message carries the IdP's `error_description` and Hono's default handler would echo it. `OIDC_REDIRECT_URI` defaults to the full URL `http://localhost:<PORT>/oidc/callback` (a path-only value would be resolved against the request's Host by the library); a configured value whose pathname is not `/oidc/callback` is a startup error.
7. **Logout.** The admin shows no logout button in external mode, so the example's own `GET /` page shows the signed-in user, a link to `/admin/` and a POST form to `/oidc/logout`. `POST /oidc/logout` is protected by `hono/csrf` (Origin check; the library's session cookie has no `SameSite`), calls `revokeSession(c)` and redirects 303 to `/`. It does not end the IdP session (no RP-initiated logout in the library). Changed 2026-10-10 (design review): Origin-only protection without a `_csrf` token is an example-level choice (the example has no CSRF token store, and logout is the only state-changing route); the CLAUDE.md rule "Every POST passes the Origin check and the `_csrf` token check" is scoped to the library's admin routes (`src/`).
8. **App origin.** The app stays plain `http`, bound like the first example (`HOST` default `127.0.0.1`, `hostGuard`), and is opened at `http://localhost:<PORT>/admin/` (not `127.0.0.1`), because browsers exempt only `localhost` from the `https:` requirement of `Secure` cookies.
9. **Shared admin.** `example/app.ts` gains `createExampleAdmin({ secret, auth })` (DB, seed, all registrations); `createExampleApp` keeps its signature and calls it with `verifyCredentials`. The OIDC app calls it with `getUser` + `loginUrl`.
10. **vitest.** `vitest.config.ts` adds `globalSetup: ["test/helpers/oidc-global-setup.ts"]` (writes the certificate, sets `NODE_EXTRA_CA_CERTS` and `OIDC_MOCK_CERT_DIR`, removes the directory on teardown) and pins `pool: "forks"` with a comment: forks is already the default, but the extra CA is read only when a worker process starts, and `threads` fails. It applies to the whole run (about 20 ms; other tests make no TLS connections). The flow test runs in the existing CI `verify` job with no network access (IdP on loopback, app in-process via `app.fetch`).
11. **Docs.** README "Development" gains an "OIDC example" subsection with the user's caveats. No CHANGELOG entry: the published files do not change. The user's browser check is described in point 14. Example texts (the `/` page, startup lines, errors) are English literals, not library UI strings.
12. **Sign-in allowlist (Q21; added 2026-10-10).** `OIDC_ALLOWED_SUBJECTS` (comma-separated, exact case-sensitive `sub`) and `OIDC_ALLOWED_EMAIL_DOMAINS` (comma-separated, exact lowercased domain after the email's last `@`, and only when the ID token says `email_verified: true`, kept in the session by a claims hook that extends the library's default). A user matching either list is allowed. With a real IdP (`OIDC_ISSUER` set) and both lists empty, the example refuses to start with a message naming both variables. Independently, `createOidcExampleApp` with an empty allowlist denies everyone, so a programmatic caller also fails closed. Mock mode defaults to subjects `["demo"]` when neither variable is set. A signed-in user who is not allowed gets a 403 "Access denied" page (naming the account, with a sign-out form) from `/oidc/login` and from the `/admin/*` bridge, which then does not call the admin; the session is not revoked automatically. Environment parsing moves into a pure `readOidcExampleConfig(env)` (`example/oidc/config.ts`) so the empty-allowlist rule is unit-tested.
13. **No logout link in the library (Q20; added 2026-10-10).** No `auth.logoutUrl` now; point 7 stands.
14. **User check (Q19; added 2026-10-10).** A manual browser run of `pnpm example:oidc` by the user (Chrome or Firefox: sign in as `demo`, see the admin, sign out) is part of acceptance as a post-implementation user check, not an implementer DoD item.
15. **Explicit library settings (added 2026-10-10, design review).** `createOidcExampleApp` takes `Required<OidcAuthEnv>` and `config.ts` fills every key (the library defaults made explicit, `""` for unset optional URL/domain keys), so `@hono/oidc-auth`'s per-key `process.env` fallback never applies; only the variables in the example's table have an effect, and tests also clear `OIDC_*` from `process.env`. Real mode requests `openid email` unless `OIDC_SCOPES` says otherwise (the library default would request every scope the IdP lists); mock mode keeps `openid email offline_access`.

## Alternatives considered
- TLS proof by string scan only (first design): misses verification turned off by an unlisted mechanism (dispatcher options, a concatenated name, package-manager settings); the negative control catches all of them at the cost of one more generated certificate and server in the test.
- Dropping `NODE_TLS_REJECT_UNAUTHORIZED` from the child's environment in the launcher: protects the demo but not a direct `server.ts` run, and silently changes the user's environment; refusing with a clear message is explicit and needs the same single exemption.
- Callback errors through Hono's default handler: no code, but echoes IdP text and leaves flow cookies behind.
- Failing the test run when unexpected `OIDC_*` variables are set: catches the shell problem but not the demo's; passing every key fixes both.
- Allowlist when empty with a real IdP (point 12): deny every user at request time is also fail closed, but the operator learns about the mistake only after a full IdP round trip ends in 403 for everyone, possibly much later; refusing to start shows it at once and names the variables. The app-level deny-all stays as a second layer.
- Allowlist shape: subjects only is the strictest, but `sub` values are opaque and hard to find; exact emails are as unsafe as domains without verification; domains without `email_verified` would trust addresses an IdP may not have verified (general concern, unverified per IdP). Group or role claims differ per IdP and were not requested.
- Denial handling: leaving a denied user out of the `WeakMap` only would make the admin redirect to `/oidc/login`, which redirects back to the admin (a loop); hence the explicit 403 from both places. Revoking the session on denial would lose the account name on the page and still leave the IdP session.
- `NODE_TLS_REJECT_UNAUTHORIZED=0` (worked in research): rejected by the user; disables verification process-wide.
- http issuer: impossible, `oauth4webapi` refuses non-HTTPS requests and `@hono/oidc-auth` offers no switch.
- Committed key and certificate: no extra dependency, but a private key in git (secret scanners) and an expiry date (unverified).
- `oauth2-mock-server` / hand-written jose mock: no `scopes_supported` (500 in `@hono/oidc-auth`) / untested fidelity.
- Bridge via `AsyncLocalStorage` holding the Hono context: works without the shared `Request`, but Node-only machinery for what a `WeakMap` does; via re-verifying the `oidc-auth` JWT from the raw `Cookie` header with `hono/jwt`: duplicates library internals and skips the refresh path; via `oidcAuthMiddleware()` on `/admin/*`: redirects straight to the IdP and bypasses `loginUrl` and `next`.
- Importing `safeNext` from `../src/auth/redirect.js`: no copy, but it is internal and a reader cannot do the same from the package (user decision against).
- Callback handled implicitly by `oidcAuthMiddleware` on the redirect path: works, but `processOAuthCallback` on a named route is easier to read.
- `GET /oidc/logout` link: simplest, but cross-site requests could log the user out (logout CSRF); a POST with the Origin check costs one small page.
- A separate vitest project for the OIDC test with its own pool and globalSetup: isolates the setup, but adds project configuration while forks is already the default for every test.
- Listening on a port for the app in the test: closer to a real run, but `app.fetch` with a cookie jar is enough (the IdP never calls the app) and avoids a second port.

## Rationale
- `@hono/oidc-auth` 1.10.0 fits hono 4.13.13 and needs only `oauth4webapi`; `getAuth` needs a Hono context (evidence: 2026-10-09-hono-oidc-auth-package). Its types resolve through a `.d.mts` next to the `import` entry and it augments hono's `ContextVariableMap` (evidence: 2026-10-09-oidc-example-package-types).
- HTTPS is mandatory for the issuer (evidence: 2026-10-09-oidc-auth-http-issuer). The run-time certificate plus `NODE_EXTRA_CA_CERTS` passed the full flow in a launcher and in vitest forks, failed under threads, and a negative control proved the trust came from the extra CA (evidence: 2026-10-09-extra-ca-certs-flow, 2026-10-09-selfsigned-cert-generation).
- oidc-provider can be driven by `fetch` with a cookie jar, needs explicit scopes, `issueRefreshToken`, `revocation` and `conformIdTokenClaims: false`, and keeps its own session after an app logout (evidence: 2026-10-09-oidc-provider-mock-idp, 2026-10-09-oidc-auth-oidc-provider-e2e); oauth2-mock-server lacks `scopes_supported` (evidence: 2026-10-09-oidc-mock-alternatives).
- A sub-app mounted with `app.route` sees the same `Request`; `app.use("/admin/*")` also covers `/admin`; a cookie set before `next()` reaches the sub-app's responses (evidence: 2026-10-09-oidc-auth-oidc-provider-e2e, 2026-10-09-oidc-example-runtime-checks).
- `continue` is the unvalidated request URL; the login-route pattern returned to a validated `next` (evidence: 2026-10-09-hono-oidc-auth-package, 2026-10-09-oidc-auth-oidc-provider-e2e). A path-only redirect URI is resolved against the request URL, and client authentication is `client_secret_basic` (evidence: 2026-10-09-oidc-example-package-types; source reading, not run).
- `Secure` cookies over `http://localhost` work in Chromium and Gecko, reportedly not in Safari (evidence: 2026-10-09-secure-cookie-localhost-browsers). Node reaches a `127.0.0.1`-bound server through `localhost` (evidence: 2026-10-09-oidc-example-runtime-checks); browsers doing the same is unverified.
- The library's default claims hook keeps only `sub` and `email`; a custom hook set on the context can add `email_verified` and runs on the callback and on each refresh (evidence: 2026-10-09-oidc-example-package-types; source reading, exercised by the mock-IdP tests once implemented).
- The library resolves each setting as `config ?? process.env`, treats `""` as unset for the optional URL/domain keys, and turns IdP callback errors into an `HTTPException` whose message holds the IdP's description (evidence: 2026-10-09-oidc-example-package-types). An untrusted self-signed leaf is rejected by Node's `fetch` with `DEPTH_ZERO_SELF_SIGNED_CERT` (evidence: 2026-10-09-oidc-example-runtime-checks).
- `node --import tsx` runs the child on the repo's toolchain (evidence: 2026-10-09-oidc-example-runtime-checks).
- New dev dependencies' engines allow Node 22 and none has an install script (evidence: 2026-10-09-oidc-example-package-types), so the CI `smoke-node22` job (frozen install plus tarball smoke) is unaffected; pnpm 12's handling of engines warnings is unverified.
