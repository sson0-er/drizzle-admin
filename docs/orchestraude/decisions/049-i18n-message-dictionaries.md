# 049: Per-locale message dictionaries (`en`, `ja`) passed to handlers and views per request

- Date: 2026-10-09
- Status: accepted
- Changed 2026-10-09 (design review, i18n round): new key `binary` and a `t` parameter for `formatValue` / `formatCell` (point 1, 3); the CLAUDE.md text of point 12 now lives only in the design README; the exact list of existing test assertions that change (point 10).

## Context
The UI was Japanese only: one `messages` object in `src/messages.ts`, imported directly by 21 modules (evidence: 2026-10-09-messages-usage-in-src). The user asked for English and Japanese, English by default, chosen per browser (decision 050) with a header switcher (decision 051), and no new `createAdmin` option. To be decided: the shape of the dictionaries, how the request's locale reaches handlers, forms and views, what happens to strings bound outside a request, `<html lang>`, locale-dependent formatting, and how the existing tests (which import `messages`) are migrated.

## Decision
1. Dictionaries. `src/messages.ts` holds two object literals, `en` and `ja`, with the same keys as the old `messages` object plus two new keys: `language` (accessible name of the switcher, decision 051) and `binary` (the cell text of a binary value, formerly the literal `[binary]` in `format.ts`; it contains a word, so the glyph exemption of decision 033 item 11 does not cover it). `en` is written without `as const`, so its values infer as `string` or as the function type. `export type Messages = Readonly<typeof en>`, and `ja` is declared `const ja: Messages = { ... }`, so a key missing from `ja`, an extra key or a wrong value type fails `pnpm typecheck`. Exports: `Locale = "en" | "ja"`, `LOCALES` (`["en", "ja"]`, the switcher order), `DEFAULT_LOCALE = "en"`, `isLocale(v)`, `Messages`, `MESSAGES: Readonly<Record<Locale, Messages>>`, and `LOCALE_NAMES` (`{ en: "English", ja: "日本語" }`, the endonyms shown by the switcher in every locale). `en` and `ja` themselves are module-private; code reaches them only through `MESSAGES`. The Japanese wording is the current text unchanged. The English wording follows Django admin where a counterpart exists (unverified that it matches Django word for word; implementers may refine it). English plural forms are written in the function-valued messages (`n === 1 ? ... : ...`).
2. Request plumbing. `initVars` (routes.md step 0, runs first) sets `c.var.locale = readLocale(c)` (decision 050) and `c.var.t = MESSAGES[locale]`. Every later middleware, every handler and `app.onError` (including the `minimal` error pages) read texts from `c.var.t`. Nothing else in `src/` reads `MESSAGES`.
3. Views. `PageChrome` gains `locale: Locale` and `t: Messages` (plus `currentUrl`, decision 051). Pages read `props.t`. Components that render UI text outside a page's own body take a `t: Messages` prop: `Widget`, `DisplayValue` (forms) and `BooleanMark` (icons). The cell formatters `formatValue` and `formatCell` take `t` as an argument (used for `t.binary`). `Layout` renders `<html lang={locale}>`.
4. Forms. Functions that produce error texts take the dictionary: `coerceForm(fields, body, mode, timeZone, t)`, `parseWithSchema(schema, data, t)`, `validateSubmission({ ..., t })`.
5. No translated text is bound outside a request. Module-level tables hold message keys or are functions of `t` (the list date presets, the DB-error-kind map in `routes/form.ts`). `siteTitle` is no longer resolved at `createAdmin`: `AdminState.config.siteTitle` becomes `string | null` (`null` = not configured) and the chrome shows `config.siteTitle ?? t.defaultSiteTitle` ("Site administration" / "サイト管理").
6. Developer-facing text stays English and outside the dictionaries: configuration errors thrown by `createAdmin`, `register` and finalization (`drizzle-admin: ...`), `console.error` log lines and `describeForLog` output. They are not shown in the UI and are written for the developer, not the end user.
7. Not translated (user-provided): model labels, field keys (column headers, filter headings, form labels), action names and labels, `toString` output, formatter output, `validate` messages, an action's returned `message`, a configured `siteTitle`.
8. Formatting stays locale-independent: date-times `YYYY/MM/DD HH:mm`, dates `YYYY/MM/DD`, numbers `String(value)` (evidence: 2026-10-09-messages-usage-in-src). No `Intl` locale formatting is added.
9. Flash texts are composed with the `t` of the request that queues them and shown verbatim on the next page. If the language changes between the two requests (only possible from another tab), the flash keeps the old language. Accepted.
10. Tests. Existing tests replace `import { messages }` with `MESSAGES` and `const messages = MESSAGES.en` (the default locale; requests carry no locale cookie), so their assertions keep their shape. The only other edits allowed to existing assertions are the ones listed in test-strategy.md "Migration of existing tests" (selectors scoped because every page now has the switcher form; `siteTitle` now `null`). `messages.test.ts` runs over both dictionaries. Japanese output is covered by new tests that send `da_lang=ja` (test-strategy.md, "Internationalization").
11. `src/index.ts` exports nothing new: no locale option, no locale types.
12. Project rules (CLAUDE.md, edited by a task): the text to copy is the section "Project rules affected" of `docs/orchestraude/drizzle-admin/03-design/README.md`, the only canonical version (design review, i18n round).

## Alternatives considered
- Forms and views return message keys, translated at the edge: `validate` already returns free-text strings from the user, so error maps would mix keys and texts; more types for no gain.
- Hono JSX context (`createContext` / `useContext`) to reach deep components without props: implicit, and views are specified as "plain props, no Context" (views.md); its behavior under our synchronous `String(element)` rendering was not verified (unverified). Only three components need the extra prop.
- An i18n library (i18next or similar): a dependency beyond pre-spec §3 for two locales, about 65 keys and one plural rule per language.
- An explicit `interface Messages` listing every key: the same typecheck guarantee as `typeof en`, with about 65 duplicated declarations to keep in sync.
- Keep the existing tests on Japanese by sending `da_lang=ja` from the test client by default: the bulk of the suite would then never exercise the default locale, and the helper would hide the cookie path that the i18n tests must check explicitly.
- `Intl`-based date and number formatting per locale (e.g. `10/7/2026, 2:05 PM` in English): the year-first numeric format is unambiguous in both languages, and the change would touch formatting tests without a request for it.

## Rationale
The code already funnels every UI string through one module (evidence: 2026-10-09-messages-usage-in-src), so per-locale objects behind one type keep that property and let the compiler enforce completeness. Setting the dictionary in `initVars` makes it available before the Origin check and the session middleware, so even the minimal error pages are localized. The three strings bound at module load or `createAdmin` time are the only places where a per-request value would otherwise be frozen (evidence: 2026-10-09-messages-usage-in-src).

## Consequences
- support.md (messages API), routes.md (`AdminVars.locale` / `t`, `initVars`, `onError`), routes-handlers.md, views.md (`PageChrome`, `Layout`, `BooleanMark`), forms.md (`t` parameters), admin.md (`siteTitle`), project-setup.md (README, CHANGELOG), test-strategy.md.
- Existing Japanese-speaking deployments see English until each browser switches; there is no option to change the default (user decision). The CHANGELOG states it.
- Adding a UI string means adding it to both dictionaries; the typecheck gate catches omissions.
